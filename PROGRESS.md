## Open questions / blockers
- Service worker versioning is manual: every web release that must refresh open tabs needs `CACHE_NAME` in `web/public/sw.js` changed by hand. Proposal (not done): stamp the cache name with the build's commit id during the Vercel build, and make the reload wait until the tab is idle so an open draft message is not lost. `web/src/sw.ts` is a second, unused copy (it is not part of the build) that has drifted from `public/sw.js` (it also pre-caches `offline.html`); decide whether to delete or adopt it.
- Limiter risk, now that it really limits: the GraphQL limiter allows 100 requests per minute per public address. Mobile networks in Uganda commonly put many phones behind one shared address, so legitimate users could be refused (HTTP 429) once enough of them share one. It was invisible before because the limiter did nothing. Proposal (not done): key by the signed-in user when a valid token is present (the existing user branch in `rate-limiting.ts` is dead code because the limiter runs before authentication) and keep the per-address cap for anonymous traffic, or raise the cap. Watch for 429s after this deploy.
- Production logs: DONE in code (not deployed yet), option A plus B: the production logger keeps warnings and errors and prints them as JSON on standard output (`backend/src/utils/logger.ts`, test `productionLogging.test.ts`), and `backend/scripts/render-logs.sh` reads Render's logs from a terminal with an API key kept in `~/.config/render/api-key` (tests in `renderLogs.test.ts`, including a fake API server). Watch-outs: warnings and errors now reach Render's Logs page, so anything sensitive inside them becomes visible there; `backend/src/services/faceRecognitionService.ts` logs the biometric engine's response body (`responseData`) and a stack on errors, check it before relying on this for real traffic. `backend/logs/` is not in `.gitignore`; the logger's own log files would show up as untracked if the backend is run from `backend/` in production mode.
- If Render ever changes its proxy chain the number 3 would need to change; the diagnostic (`FORWARDING_DIAGNOSTIC=true`) shows the chain again. A direct-origin bypass of Cloudflare was not found; if one existed, a caller on that path would only have a chain of two entries, and three trusted hops would then believe a forged entry.
- Web dependency heads-up: `web/package.json` allows `@apollo/client ^4.0.4` but the lockfile pins 4.0.4; with Apollo 4.3.x `tsc -b` fails in `web/src/lib/apolloClient.ts` (lines about `errorPolicy` default options). Do not refresh the web lockfile or update Apollo without fixing that; `web/package-lock.json` is also out of sync with `package.json` (`npm ci` fails). Locally `web/node_modules` was installed with `--legacy-peer-deps --ignore-scripts` for checking (gitignored).
- Retention period for `security_audit_logs` (legal requirement, not decided).
- Render's build command runs `npx prisma db push` against the live Supabase database on every deploy (not migrations). So the migration files, including the edited `20261026_session_version`, are not used by Render; `db push` already added the `sessionVersion` column to production (the 17:26 build said "already in sync"). Earlier notes saying the build runs `prisma migrate deploy` were wrong. Proposal for the developer (not done): `db push` on production skips version-controlled migrations, which is against the database rules in the global instructions; a baselined migration history plus `prisma migrate deploy` would be the proper setup, a larger change to decide separately.
